# BPTemplate — FRC 5515 Blue Power Robotics Robot Code Template

A starting point for FRC robot code, built from our 2026 robot code. It ships with a fully
working swerve drive (CTRE Phoenix 6 + Tuner X), controller bindings, PathPlanner support,
and Limelight vision pose estimation — the things every robot needs before any game-specific
code exists.

**Stack:** Java 17 · WPILib 2026 · CTRE Phoenix 6 · PathPlannerLib · AdvantageKit logging · Limelight

---

## Getting a season robot repo from this template

1. **Use the template** — click **"Use this template"** on GitHub (or "Import repository"),
   name it after the new season's robot, and clone it.
2. **Rename the team-specific bits:**
   - `src/main/java/frc/robot/generated/TunerConstants.java` — regenerate with
     [Tuner X](https://v6.docs.ctr-electronics.com/en/stable/docs/tuner/tuner-swerve/index.html)
     for your robot's modules (motor IDs, offsets, ratios, CAN bus). This file is generated
     from real hardware, so it must match your robot.
   - `src/main/java/frc/robot/Constants.java` — tune gains, filters, and field geometry;
     set `VisionConstants.LIMELIGHT_NAME` to your Limelight's NetworkTables name.
   - `.wpilib/wpilib_preferences.json` — your team number.
   - `vendordeps/` — update vendordep JSONs to the new season's versions (WPILib → Vendor Dep
     in VS Code).
3. **Deploy path:** `src/main/deploy/pathplanner/` holds PathPlanner settings and autos.
   Open the PathPlanner GUI, add your robot config, and create autos.

Build/deploy as any WPILib project: **WPILib extension → Deploy Robot Code** (or
`./gradlew deploy`), simulate with **Simulate Robot Code** or `./gradlew simulateJava`.

## What's inside — where to look first

| Path | What it is |

| `src/main/java/frc/robot/RobotContainer.java` | Wiring: subsystems, controller bindings, auto chooser |
| `src/main/java/frc/robot/subsystems/CommandSwerveDrivetrain.java` | The whole swerve brain: drive requests, move-to-pose PID, PathPlanner, vision fusion |
| `src/main/java/frc/robot/generated/TunerConstants.java` | Hardware constants (generated by Tuner X — don't hand-edit casually) |

| `src/main/java/frc/robot/commands/fineTuneDrivetrainCmd.java` | D-pad/trigger creep + rotate-in-place command |

| `src/main/java/frc/robot/LimelightHelpers.java` | Vendor's Limelight NT helper library |

## Default controls (driver 1, port 0)

| Input | Action |
|-------|--------|
| Left stick | Translate (field-centric; push up = robot-forward) |
| Right stick | Rotate |
| Back | Re-define "forward" as the robot's current facing |
| D-pad | Creep in that direction (fine adjustment) |
| LT / RT | Rotate in place, CCW / CW |

Controllers 1 and 2 (ports 1, 2) are set up but unbound — ready for operator controls.

## Studying the code: a suggested order

1. **`RobotContainer.java`** — see how a subsystem gets a default command and how button
   bindings map to commands. This is the command-based pattern in miniature.
2. **`CommandSwerveDrivetrain.periodic()`** — everything here runs every loop: operator
   perspective, vision fusion, gyro reseed.
3. **`driveFieldCentric(controller)`** — the simplest full loop: sticks → expo curve →
   velocities → a `SwerveRequest` the Phoenix library turns into module outputs.
4. **`getAutoMoveToPoseSpeeds()`** — closed-loop pose control: three PID loops (X, Y, θ)
   driving toward a pose, then clamped by `optimizeMoveToSpeeds()`.
5. **`updateOdometry()`** — how MegaTag2 vision measurements are filtered (spin/speed/tag
   distance/latency gates) and fused with a distance-scaled standard deviation.
6. **`reseedGyroByVision()`** — a niche trick: correcting gyro drift using MegaTag1 when
   confidence is high.
7. **`TunerConstants.java`** — skim to see what hardware config a swerve module needs
   (gear ratios, encoder offsets, gain slots).

## Adding your first subsystem (exercise)

1. Create `src/main/java/frc/robot/subsystems/MySubsystem.java` extending `SubsystemBase`.
2. Construct your motors in its constructor, apply configs once, write a `periodic()` that
   logs sensor data.
3. Instantiate it in `RobotContainer` and write a default command (or none, if it's passive).
4. Bind a button: `m_driverController2.a().whileTrue(new MyCommand(mySubsystem));`
5. Add any tunable numbers to `Constants` in a new nested class.

## Conventions in this codebase

- Follow the existing `CommandSwerveDrivetrain` style: subsystems extend their hardware
  class (or `SubsystemBase`) and implement `Subsystem`.
- Constants live in `Constants` nested classes, `public static final`, UPPER_SNAKE_CASE.
- Commands live in `frc.robot.commands`; one file per command.
- Keep robot-contingent logic (alliance flips, etc.) inside the drivetrain or a helper —
  not scattered through commands.
